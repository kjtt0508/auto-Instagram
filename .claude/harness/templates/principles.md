# 設計原則（P01–P35）

『現場で役立つシステム設計の原則』（増田亨）の考え方を、このリポジトリで**検査・レビューできる単位**に落とし込んだもの。
要約・解釈はこのプロジェクト独自のもの。背景や理由の詳細は原著を参照すること。章との対応は `BOOK_COVERAGE.md`。

レビュー指摘・コミットメッセージ・ADR では原則IDを引用する（例: `refactor: 金額計算を Money に移動 (P04)`）。

「強制」列: **G**=gate（書き込み前）/ **L**=lint（書き込み直後・言語パック）/ **A**=依存方向チェック（全言語）/ **T**=trace / **R**=design-reviewer / **S**=スキルの手順

アプリの性質上当てはまらない原則（DB を持たない・API を公開しない等）は `harness.yaml` の `principles.disabled` で外す。
意図的な逸脱は ADR を書き、該当行に `harness-allow: Pxx ADR-xxxx`（ファイル全体なら `harness-allow-file:`）とコメントする。

## 1. 小さくまとめてわかりやすくする（1章）

| ID | 原則 | 強制 |
|---|---|---|
| P01 | 名前は業務の言葉で、省略せずに付ける（`a`・`qty` ではなく `quantity`）。Manager / Util / Info / Data のような「何でも入る」名前を避ける | L R |
| P02 | メソッドは短く、クラスは小さく。長い処理は「段落」に分けて目的ごとのメソッドにする。変数は目的ごとに用意し使い回さない。意味のある数値（送料 500 など）は名前の付いた定数・値にする | L R |
| P03 | 同じ業務ルールを複数箇所に書かない。変更が1か所で済む置き場所を決める。共通ライブラリ（Util）に業務ロジックを集めない | L R |
| P04 | 計算・判断のロジックは、そのデータを持つクラスに置く（データとロジックを一緒にする）。使う側のクラスに業務ロジックを書き始めたら設計を見直す | L R |
| P25 | 引数を少なくする。引数が多いのは関心事が混ざっている兆候。関連する引数は値オブジェクトにまとめる | L R |

## 2. ドメインオブジェクト（1–3章）

| ID | 原則 | 強制 |
|---|---|---|
| P05 | int / String / BigDecimal をそのまま業務の値に使わない。業務上の桁数・範囲を持つ値（数量・金額・電話番号など）は値オブジェクトにして型で区別する | L R |
| P06 | 値オブジェクトは不変。変更は「新しいオブジェクトを返す」で表現する | L R |
| P07 | 完全コンストラクタ：生成時に必要な値をすべて受け取り不変条件を検証する。不正な状態のオブジェクトを存在させない | T R |
| P08 | コレクションは専用クラスで包む（ファーストクラスコレクション）。コレクションの操作は業務の関心事として名前を付ける | L R |
| P09 | 区分ごとに変わる振る舞いは区分オブジェクト（enum 等）に持たせ、区分ごとのクラスを同じ型として扱う。if/switch を散在させない | L T R |
| P10 | 状態と遷移ルールは enum 等で表現し、「遷移できるか」を状態自身に判断させる | T R |
| P11 | 判断・加工の条件は名前の付いたメソッドや業務ルールオブジェクト（仕様）に切り出す | R |
| P12 | 尋ねるな、命じよ。getter で値を取り出して外で判断しない。setter を作らず、変更は業務の言葉のメソッドで | L R |
| P13 | null を返さない・受け取らない。「未設定」「該当なし」は型で表す | L R |
| P14 | 契約による設計：前提条件はドメインオブジェクトが保証する。呼び出し側で同じ防御的チェックを重複させない | R |
| P26 | 場合分けは単純に：else 句を使わず早期リターン（ガード節）にする。&& と \|\| が混ざった複文は名前の付いた単文の判断メソッドに分ける。ネストを浅く保つ | L R |
| P27 | メソッドは必ずインスタンス変数を使う。使わないメソッド（static な計算）は、そのデータを持つクラスへ移す | L R |
| P28 | パッケージは業務の関心事で分ける（注文・請求・在庫…）。dto / entity / util / enums のような技術的な種別で分けない | L R |

## 3. ドメインモデルの考え方（4章）

| ID | 原則 | 強制 |
|---|---|---|
| P29 | ドメインオブジェクトは「ヒト・モノ・コト」で見つけ、**コト**（取引・約束・出来事）を中心に業務ルールを集める。コトごとに「約束すること・約束しないこと」を明示する。ドメインオブジェクトを画面や機能の一部として設計しない | T S R |
| P22 | 業務の関心事を起点に、重要な部分から、部分と全体を行き来しながら分析→設計→実装→テストを短いサイクルで反復し、モデルとコードを一致させ続ける | G T S |
| P23 | 用語集（domain.yaml）の言葉をコード・ドキュメント・会話で統一する。業務の言葉をキャッチし、あいまいな言葉は具体例・数値・境界で具体化する。言葉がずれたらモデルを直す | G T S |

## 4. アプリケーション機能の組み立て（5章）

| ID | 原則 | 強制 |
|---|---|---|
| P15 | アプリケーションサービスは業務ロジックを持たず、ドメインオブジェクトの取得・組み立て・保存の調整に徹する。登録系と参照系に分け、小さく保つ | L R |
| P30 | 画面や外部の多様な要求は小さなサービスに分け、それらを組み立てる**シナリオ**（ユースケースの手順）で実現する。利用する側と提供する側の合意（入出力・事前条件）を明確にする | S R |
| P16 | 画面・DB・外部API の都合をドメインに持ち込まない。依存の向きは「外側 → ドメイン」。データベース操作ではなく業務の関心事（リポジトリ）で考える | A L |

## 5. データベース（6章）

| ID | 原則 | 強制 |
|---|---|---|
| P17 | DB は事実を正確に記録する場所。NOT NULL・一意・外部キー・CHECK 制約を徹底し、NULL 許容には理由を書く（多くは別テーブルに分けられる） | L R |
| P18 | 上書きより追記。記録の変更を禁止し、UPDATE を使わない。状態・残高は「コト」の記録から導出する（同時に・1か所で更新しなくてよい） | L R |
| P19 | テーブルは関心事ごとに分ける。用途のわかりにくいカラム・巨大テーブル・フラグの乱立を避ける | L R |
| P31 | 記録のタイミングが異なるデータはテーブルを分け、カラム追加ではなくテーブル追加で拡張する。オブジェクトとテーブルは違うものとして明示的にマッピングする（業務ロジックはオブジェクトで、事実の記録はテーブルで） | L S R |

## 6. 画面（7章）

| ID | 原則 | 強制 |
|---|---|---|
| P32 | 画面はタスク単位に小さく分け、画面の関心事（項目・並び順・グルーピング・状態ごとの見せ方）をドメインオブジェクトと連動させる。表示のための判断はドメインに置き、画面に業務ロジックを書かない。画面とドメインの食い違いは設計改善の手がかりとして扱う | L S R |

## 7. アプリケーション間の連携（8章）

| ID | 原則 | 強制 |
|---|---|---|
| P20 | API はアプリケーション間の契約。万能な API（One Size Fits All）を作らず、利用側が組み立てやすい小さな部品として設計し、ドメインの言葉で命名し、内部構造を露出しない | S R |
| P21 | 境界で入力を値オブジェクトに変換して検証する。導出結果を返すか生データを返すかを明示する | S R |
| P33 | 連携方式（ファイル転送・DB 共有・Web API・メッセージング）を目的で選ぶ。API は単純なものから始め、仕様（OpenAPI 等）で利用側と合意し、バージョンを管理して動かしながら発展させる | S R |

## 8. 開発プロセス（9–10章）

| ID | 原則 | 強制 |
|---|---|---|
| P24 | 業務ルールはドメインオブジェクトの単体テストで厚く検証し、テストを仕様として読めるようにする。受入基準とテストを紐付ける | T |
| P34 | ソースコードを第一級のドキュメントにする。別に更新し続ける文書は用語集・全体俯瞰・判断記録（ADR）に絞る。非機能要件はテストコードで表現する | T S |
| P35 | 設計は一度で完成させず、少しずつ改良し続ける。リファクタリングは部分的に小さく、テストで守りながら行う。変更のたびに変更しやすくする | S R |
