# アプリケーション間の連携（P20 P21 P33）

## 1. 連携方式を目的で選ぶ
| 方式 | 向いている場面 | 注意 |
|---|---|---|
| ファイル転送 | 日次・月次の大量データ、相手が古いシステム | 形式と受け渡しの約束（文字コード、件数、再送）を文書化 |
| データベース共有 | 原則避ける | テーブルが契約になり、双方が変更できなくなる |
| Web API（同期） | 利用側がすぐ結果を必要とする | 相手の障害・遅延が自分に波及する。タイムアウトと縮退を決める |
| メッセージング（非同期） | 出来事の通知、処理を待たなくてよい連携、疎結合 | 順序・重複・再送を前提に冪等に作る |
コト（出来事）の通知はメッセージング、問い合わせは Web API、が基本の組み合わせ。

## 2. HTTP の約束事を守る
- **URI** = 業務の対象（`/orders/{orderNumber}`）。動詞はタスクとして明示してよい（`POST /orders/{n}/cancellation`）
- **メソッド** = 要求の種類（GET 参照 / POST 作成・タスク実行 / PUT 置換 / DELETE）
- **ステータスコード** = 結果（200/201/204、400 入力不正、404、409 状態が許さない、422 業務ルール違反、503 縮退）
- **エラー形式**を全 API で統一（例: RFC 9457 Problem Details: type / title / detail / 項目別エラー）
- **表現形式** = JSON。項目名は用語集の英語名（code_name）に揃える

## 3. 良い API
- **One Size Fits All を作らない**。あらゆる用途を1つの巨大 API で満たそうとせず、利用側が組み立てやすい**小さな部品**を提供する。
- **単純なことを簡単に**できる API から始め、**動かしながら**発展させる。最初から全部を設計しない。
- 利用側と提供側が**共同作業できる環境**を用意する: OpenAPI 仕様をリポジトリに置き、Swagger UI 等で試せるようにする。仕様がそのまま合意文書になる。
- **中核 API のセット**を先に固め、個別要件は中核の組み合わせ（複合 API / BFF）で応える。共通部分と個別対応部分を分ける。

## 4. ドメインオブジェクトとデータ形式の変換
- ドメインオブジェクトをそのままシリアライズしない（lint がドメインの JSON/永続化アノテーションを検出する）。presentation 層で Request/Response 型に変換する。
- 入力は境界で値オブジェクトに変換し、変換失敗は 400 / 422 に（P21）。
- **導出結果か生データか**を決めて仕様に書く。例: 注文金額（導出結果）を返すのか、単価と数量（生データ）を返して利用側で計算させるのか。業務ルールを利用側に複製させたくないなら導出結果を返す。
- 不一致（ドメインの粒度 ≠ 利用側が欲しい粒度）は、API 側に専用の Response 型を作って吸収する。ドメインを利用側の都合で変えない。

## 5. バージョン管理と進化
- 追加は後方互換（項目追加・任意パラメータ追加）。削除・意味の変更は破壊的変更 → 新バージョン（`/v2/` またはメディアタイプ）。
- 旧バージョンの廃止予定日を決め、リリースノートに書く。
- 大きくなったら、小さなアプリケーションに分けて API で組み合わせることを検討する（分割はコト単位が境界になりやすい）。

## 6. 非同期メッセージング
- メッセージ = コトの発生通知（`OrderPlaced`）。用語集の event として定義する。
- 受信側は重複・順序入れ替わりを前提に冪等に処理する。スキーマもバージョン管理する。

## 出力
- design.md の「外部との契約」節、`docs/api/openapi.yaml`（または各言語のアノテーションから生成）
- 契約テスト（入口のテスト）に受入基準 ID を付ける
