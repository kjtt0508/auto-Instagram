# 01 要件定義 — 業務の関心事から始める（P22）

画面やテーブルから考えない。**業務の人が何を気にしているか**（関心事）と、**守るべきルール**を言葉にする。

## 手順
0. 業務をまだよく知らない場合は、先に `/domain-discovery` で言葉を集め、ヒアリング項目を作る。
1. `.claude/harness/templates/requirement.yaml` を `docs/requirements/REQ-<3桁>.yaml` にコピー（既存番号の次）。
2. ユーザーにヒアリングする。一度に聞くのは1〜2問。聞くこと:
   - 何に困っているか（background）／誰が使うか（actors）
   - 業務として何を気にしているか（concerns）— 「正しく」「漏れなく」「早く」の具体
   - 計算・判断・加工のルール（business_rules）— 数値の範囲、端数、例外、区分ごとの違い
   - 区分・状態の洗い出し: 「種類によって扱いが変わるものは？」「どんな状態を経る？ 戻れる？」
3. 業務ルールに出てくる**名詞**を `terms` に列挙する。同じものを別の言葉で呼んでいたら、ユーザーにどちらを正とするか確認し、もう一方は後で domain.yaml の `avoid` に入れる。
4. 受入基準を Given/When/Then で書く。**境界値と異常系**を最低1つずつ（例: 数量 0 / 1 / 99 / 100）。
5. 非機能要件（性能・冪等性・同時実行・可用性）は `NFR-xxx-xx` の ID と `verify_by` を付ける。テストで表現できるものは `verify_by: test`（P34）。
6. 決めきれないことは `open_questions` に残す。推測で埋めない。あいまいな言葉（「通常」「すぐに」「大口」）は具体例・数値・境界で置き換える。
7. `python3 .claude/harness/harness.py trace` を実行（用語未定義エラーはこの時点では想定内 → 工程02で解消）。
8. `design-reviewer` サブエージェントに要件レビューを依頼する。
9. open_questions が空になり、ユーザーが合意したら `status: approved` にする。**承認はユーザーの明示的な同意で行う。**

## 良い要件のチェック
- [ ] 業務ルールが「画面の項目」ではなく「業務の言葉」で書かれている
- [ ] 数値ルールに範囲・単位・端数処理がある
- [ ] 区分ごとに振る舞いが違うものが明示されている（→ 区分オブジェクト候補 P09）
- [ ] 状態と遷移の可否が書かれている（→ 状態 enum 候補 P10）
- [ ] 受入基準がテストとして自動化可能な具体値を持つ
