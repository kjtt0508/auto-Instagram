# 分析と設計が一体になった開発をマネジメントする（P22 P34）

V 字モデルの工程完了ではなく、**動くソフトウェアと業務ルールの検証状況**で管理する。

## 1. 進捗の判断
`python3 .claude/harness/harness.py overview` で `docs/overview.md` を生成し、次で報告する。
- 受入基準のうちテストで検証済みの割合（= 業務として動く範囲）
- 承認済み要件数 / 全要件数、用語集の成長（業務理解の進み具合）
- 未解決の整合性エラー（モデルとコードのずれ）
「設計書の完成度」「コード行数」は進捗の指標にしない。

## 2. 見積もり
- 単位はユースケース（シナリオ）と受入基準。用語の数（特にコトと状態・区分）が複雑さの指標になる。
- 初期のドメインモデルは力不足であることを前提に、**モデルを育てる時間**（リファクタリング・用語の見直し）を見積もりに含める。
- 不確実な部分は、重要な部分から小さく作って確かめてから見積もり直す。

## 3. 契約
- 成果物を「全機能の一括」で固定するより、反復ごとに優先度の高いユースケースから届ける形（準委任・段階契約）が相性がよい。
- 請負の場合も、受入基準（Given/When/Then）を合意文書にし、自動テストで検収できるようにする。

## 4. 品質保証
- 業務ルール: ドメインの単体テスト（受入基準・非機能要件の ID で紐付け）
- 構造: ハーネスの lint・依存方向チェック・（任意で）ArchUnit 等
- 設計判断: design-reviewer のレビュー記録、ADR
- `verify` の成功記録（`.harness/last_verify.json`）がリリース可否の根拠

## 5. ドキュメント方針
| 残す（更新し続ける） | 残さない（コードが正） |
|---|---|
| 用語集（domain.yaml） | クラス図・詳細設計書・画面項目定義の手書き版 |
| 全体俯瞰（overview.md、自動生成） | コードと同じ内容を文章にしたもの |
| 要件と受入基準（REQ） | |
| 設計判断（ADR）、外部契約（OpenAPI） | |
技術方式もできるだけコード（設定・テスト・ハーネス）で表現し、非機能要件はテストコードで表現する。
顧客や社内の規程で成果物が求められる場合は、上の「残す」ものから生成する（overview の出力、用語集の表形式変換）。

## 6. 要員と体制
- 業務の人と開発者が**同じ言葉**で話せるように、用語集のオーナーを決める。
- ドメインモデルを担う人を固定しすぎない。レビュー（design-reviewer と人のレビュー）で設計の考え方を共有する。
- オブジェクト指向設計に不慣れなメンバーには design-coach エージェントと /refactor の練習（calisthenics プロファイル）を使う。
