# 03 設計 — ドメインの外側を決める（P15–P21）

テンプレート: `.claude/harness/templates/design.md` → `docs/design/REQ-xxx.md`。**コードを読めば分かることは書かない**。
アプリの形（Web API / SPA / CLI / バッチ / モバイル / ライブラリ）に関係なく、次の4つの境界を決める。

## 1. ユースケース（アプリケーション層）P15
- ユースケース1つ＝入口1つ（サービスのメソッド、ハンドラ、コマンド）。参照系と更新系を分ける。
- 中身は「取得 → ドメインオブジェクトに命じる → 保存/通知」だけ。if や計算が必要になったら、ドメインに置き場所が無い兆候 → 工程02に戻る。

### シナリオで組み立てる（P30）
- 画面や外部の多様な要求を、小さなサービス（登録系・参照系）に分け、それらを**シナリオ**（ユースケースの手順）で組み立てる。
- 利用する側と提供する側の合意（入力・事前条件・結果・失敗時）を design.md のシナリオ表に書く。
- サービスを作りながら、ドメインモデルの力不足（サービスに if が溜まる）を見つけて /p2-model に戻す。

## 2. 画面（P32）
詳細は `/ui-design`。画面をタスク単位に分け、画面の項目グループ・状態ごとの見せ方をドメインオブジェクトに対応させる。

## 2b. 外部との契約（API・CLI・メッセージ）P20 P21 P33
詳細は `/api-design`。連携方式（ファイル/DB 共有/Web API/メッセージング）を目的で選ぶ。
- 利用側が**何をしたいか**の単位で切る。保存先の構造（テーブル単位の CRUD）をそのまま出さない。
- 名前は用語集の言葉。入力は境界で値オブジェクトに変換し、変換失敗は入力エラーとして返す。ドメインに生の文字列・数値を流さない。
- 更新系は冪等性（リトライで二重登録しない）、公開 API はバージョニングと後方互換を決める。

## 3. 永続化 P17–P19 P31（RDB / NoSQL / ファイル / 外部SaaS どれでも）
詳細は `/db-design`。
- 保存単位は「記録する事実（コト）」。記録のタイミングが違うものはテーブルを分け、カラム追加ではなくテーブル追加で拡張する。
- 状態変化は履歴・イベントとして追記し、UPDATE で上書きしない。状態・残高は記録から導出する。
- 欠損（NULL / 省略可能項目）を基本的に許さない。必要なら、その値が無いケースを別の記録に分けられないか先に検討。
- 区分・状態は値域を制約で守る。フラグを並べない。
- ドメインモデルと保存形式は一致させなくてよい。変換は infrastructure で行う。
- 永続化を持たないアプリなら `harness.yaml` の `principles.disabled` に P17–P19 を入れて「該当なし」と書く。

## 4. 異常系・外部依存
- 外部サービスの失敗・遅延時にどう縮退するか。各異常系を受入基準に対応付ける。

## ADR
トレードオフのある判断（不変の例外、欠損の許容、非同期化、縮退方針、原則からの逸脱）は `.claude/harness/templates/adr.md` で `docs/adr/` に残す。
