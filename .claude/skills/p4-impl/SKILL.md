# 04 実装 — ドメインから内側→外側へ

## 順序（1ユースケースずつ縦に通す）
1. **ドメイン**: 用語集の用語を型にする。同時に単体テストを書く（テスト先行推奨）。
2. **アプリケーション**: ユースケースを調整するだけの薄い層。
3. **インフラ**: リポジトリ実装・マイグレーション・外部API クライアント（ドメインが定義したインターフェースを実装）。
4. **プレゼンテーション**: 入口（Controller / Handler / 画面 / CLI）で入力を値オブジェクトへ変換。
5. **UI 側のドメイン**（SPA 等がある場合）: UI 非依存のロジックだけを domain に。

## 実装パターン
まず `references/patterns.md`（言語共通の考え方と対応表）を読み、次に使う言語のファイルを読む:
`patterns-java.md`（Kotlin も参照可） / `patterns-typescript.md` / `patterns-python.md` / `patterns-go.md` / `patterns-csharp.md` / `patterns-php.md` / `patterns-ruby.md`

## 書き方の基本（1〜3章）
- 名前は業務の言葉で省略しない。長い処理は段落に分けてメソッドにする。意味のある数値は定数・値に（P01 P02）。
- 引数は少なく（P25）。else を使わずガード節、複文は判断メソッドに（P26）。
- メソッドはインスタンス変数を使う。使わないなら置き場所が違う（P27）。
- パッケージは業務の関心事で切る（`order/`, `billing/`）。`dto/`, `util/` を domain に作らない（P28）。
- アプリケーション層はシナリオ（ユースケースの手順）を組み立てるだけ（P15 P30）。リポジトリは業務の関心事の言葉で（`findUnshippedOrders()`、SQL の言葉ではなく）。
- 画面の実装は `/ui-design`、API は `/api-design`、テーブルとマイグレーションは `/db-design`、既存コードの改善は `/refactor`。

## フックとの付き合い方
- **書き込み前に拒否（モデル先行）** → 用語集に無い型。既存用語の名前を使うか、`/p2-model` で用語を追加（ユーザーに確認）。
- **書き込み後にブロック（lint エラー）** → 原則IDの指摘に沿って直す。回避用の書き換え（名前を変えただけ等）はしない。
- **警告** → 基本は直す。意図的に残す場合は ADR を書き `harness-allow: Pxx ADR-xxxx` コメント。
- 依存方向違反（P16）は import を消すのではなく、依存を逆転させる（ドメインにインターフェースを置き、インフラで実装）。
