# 業務を学びながらドメインモデルを育てる（P22 P23 P29）

業務知識は最初から揃っていない。**言葉をキャッチ**し、**重要な関心事に絞って**学び、**繰り返しながら**広げる。

## 1. 言葉をキャッチする
入力（会話・議事録・メール・既存画面・帳票・マニュアル）から、次を拾って `docs/model/glossary-inbox.md` に溜める（まだ domain.yaml に入れない）。
- 業務の人が**繰り返し使う名詞**（注文、引当、締め、請求…）と**動詞**（受け付ける、引き当てる、締める…）
- 同じものを指す**別の言い方**（受注 / オーダー / 注文）→ どれを正とするか要確認
- **区分**を示す言葉（〜の場合、〜のときは、種類、区分、ランク）
- **状態**を示す言葉（〜済み、〜中、保留、取消）
- **数値ルール**（上限、下限、何日以内、端数、率）
- 例外を示す言葉（ただし、特別に、〜だけは、原則として）← 業務ルールの宝庫

## 2. 重要な関心事を見極める
全部を同じ深さで学ばない。次の順で優先する。
1. **コト**（取引・約束・出来事: 注文、契約、予約、出荷、請求、入金）— 業務ルールが集まる
2. コトの**当事者（ヒト）と対象（モノ）**
3. コトの**状態の移り変わり**と、状態ごとにできること
4. お金・数量・期限に関わる計算

「このシステムが無くなったら、業務の人は何を一番困るか」を聞くと中核が見える。

## 3. ヒト・モノ・コトで分類する
| 分類 | 例 | 見つけ方 | 設計上の注意 |
|---|---|---|---|
| ヒト | 顧客、会員、担当者、取引先 | 「誰が」「誰に」 | 属性の寄せ集めにしない。コトとの関係で必要な情報だけ |
| モノ | 商品、在庫、設備、口座 | 「何を」 | 価格など変わる属性は、コト側に記録時点の値を持たせる |
| コト | 注文、予約、契約、出荷、支払 | 「いつ」「何をした/約束した」 | 業務ルールの中心。発生日時・当事者・対象・約束を持つ |

各コトについて **約束すること / 約束しないこと** を確認する（例: 注文は受付時の単価で金額を確定する／配達日時は約束しない）。
「何でも約束してよいわけではない」— 約束の範囲を決めることが業務ルールを決めることになる。

## 4. 暗黙知を引き出す質問
ヒアリング項目は `references/questions.md` のテンプレートから作る。基本は次の型:
- **具体例を1件**: 「先週あった一番普通の注文を1件、最初から最後まで教えてください」
- **例外を探す**: 「その流れにならなかったケースは？」「一番困った注文は？」
- **境界を聞く**: 「99個はOK？100個は？」「締め日の23:59は当月？」
- **理由を聞く**: 「なぜそのルールがあるのですか」（理由が分かると例外の扱いが決まる）
- **現物を見る**: 実際の帳票・画面・Excel を見せてもらう。「ここに手書きしている欄は何ですか」

## 5. あいまいさを具体化する
あいまいな言葉を見つけたら、**具体例・数値・境界・反例**のどれかで置き換えるまで確定しない。
| あいまいな言葉 | 具体化の問い |
|---|---|
| 「通常は」「基本的に」 | 通常でないのはどんなとき？ 年に何回？ |
| 「すぐに」「早めに」 | 何分/何日以内？ 過ぎたらどうなる？ |
| 「大口」「VIP」 | 基準は金額？ 回数？ 誰が決める？ |
| 「適切に」「必要に応じて」 | 誰が何を見て判断する？ その判断をシステムがする？ |

## 6. 形式的な資料に頼りすぎない
網羅的な資料（全項目定義書、全画面一覧）は、重要でないものと重要なものを同じ重さで並べてしまう。
資料は**言葉を拾う素材**として使い、重要度はヒアリングで決める。

## 7. 基本語彙を増やす
業務分野の典型的な概念（`references/vocabulary.md`）を知っておくと、ヒアリングで「〜のようなものはありますか」と聞ける。

## 出力
- `docs/model/glossary-inbox.md`（拾った言葉・出典・未確認事項）
- 確定した用語は `/p2-model` で domain.yaml へ、業務ルールは `/p1-req` で要件へ
