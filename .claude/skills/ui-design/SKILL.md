# 画面とドメインオブジェクトを連動させる（P32）

画面には利用者のさまざまな関心事が詰め込まれやすく、画面に引きずられた設計は変更を大変にする。
**画面の関心事を小さく分け**、**ドメインオブジェクトと一対一に近づける**。

## 1. 画面を小さく分ける（タスクベース）
- 1画面に「照会・入力・承認・集計」が混ざっていたら、関心事ごとに分ける。**画面自体を分けてよい**。
- 「何でもできる編集画面」ではなく、利用者のタスク単位にする（例: 「住所を変更する」「注文を取り消す」）。
  - タスクに業務の名前が付き、ドメインの業務メソッド（`relocate()`, `cancel()`）とアプリケーションサービスに対応する。
  - 変更の範囲がタスク単位に閉じ、権限・監査・API もタスク単位で設計できる。
- 設計書（design.md の「画面」節）に、画面ごとの**利用者の関心事**と**対応するドメインオブジェクト**を書く。

## 2. 表示のための判断はドメインに置く
画面に `if (status === "CANCELLED")` や `price * quantity` を書かない（lint が警告する）。
| 画面で必要なもの | 置き場所 | 例 |
|---|---|---|
| 計算結果 | ドメインのメソッド | `order.totalAmount()` |
| 状態ごとの見せ方 | 状態オブジェクト | `status.label()`, `status.cssClass()`, `status.canCancel()` |
| 表示用の書式 | 値オブジェクト | `money.displayText()` → "1,000円" |
| 項目の出し分け | ドメインの判断メソッド | `customer.isMember()` |
- HTML の class 属性（`is-cancelled` など）を状態オブジェクトから出力すると、見た目と論理構造が一致し、状態の追加が1か所で済む。
- API 経由の SPA なら、presentation 層のレスポンス（View Model）で上の値を作ってから返すか、フロントの `domain` に同じ状態オブジェクトを置く。

## 3. 項目の並び・グルーピングをドメインと揃える
- 画面の項目グループ = 値オブジェクトやエンティティのまとまり（例: 「お届け先」グループ = `DeliveryAddress`）。
- 画面の項目の並び順とドメインオブジェクトのフィールド順を揃えると、対応が読み取りやすくなる。
- **食い違いは設計改善の手がかり**: 画面では1グループなのにドメインでは散らばっている → 値オブジェクトが足りない。
  画面にしかない言葉 → 用語集に無い業務概念かもしれない（/p2-model へ）。

## 4. 画面以外の利用者向け情報も揃える
ラベル・エラーメッセージ・ヘルプ・マニュアル・帳票の言葉を用語集に揃える（用語ドリフトは trace が検出）。
エラーメッセージは完全コンストラクタ・仕様オブジェクトの検証メッセージを元にすると、ルールと説明がずれない。

## 5. デザインと設計を一緒に洗練する
デザイナーと画面を詰めるとき、近接（関連する項目を近くに）・整列・反復・対比の考え方で整理したグループが、そのまま値オブジェクトの候補になる。
画面デザインの変更依頼が来たら「どのドメインオブジェクトのまとまりが変わるのか」を確認する。

## チェックリスト

- [ ] 画面に計算・状態コード比較が無い（lint の P32 警告 0）
- [ ] 項目グループと値オブジェクト/エンティティが対応している
- [ ] ラベル・メッセージが用語集の言葉
