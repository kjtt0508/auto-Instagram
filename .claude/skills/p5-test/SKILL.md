# 05 テスト — 業務ルールを仕様として固定する（P24）

テストケース設計は `test-designer` サブエージェントに任せてよい。

## テストの厚み（下ほど多く）
| 層 | 対象 | 何を確かめるか |
|---|---|---|
| E2E | 主要な受入基準のみ | 利用者の操作で業務が完了するか |
| 契約 | 入口（API / Handler / CLI） | 入力変換・エラー形式・ステータス |
| 永続化 | リポジトリ実装 | 制約・マッピング・追記型の記録（本物に近い DB で） |
| アプリ | ユースケース | 調整の順序・トランザクション境界（リポジトリはインメモリ実装） |
| **ドメイン** | 値/エンティティ/区分/状態/仕様 | **業務ルールのすべて**。境界値・不変条件・遷移表 |

モックは外部 I/O だけに使う。ドメインオブジェクトはモックしない。

## 受入基準との紐付け
テスト名・タグ・コメントのどこかに受入基準ID（`AC-001-01`）を含めれば `harness trace` が検出する。
| フレームワーク | 書き方 |
|---|---|
| JUnit 5 | `@Tag("AC-001-01") @DisplayName("AC-001-01 ...")` |
| Kotest / Kotlin | `"AC-001-01 ..." { }` |
| Jest / Vitest / Playwright | `it("AC-001-01 ...", ...)` / `test("AC-001-01 ...")` |
| pytest | `@pytest.mark.ac("AC-001-01")` または関数の docstring |
| Go | `t.Run("AC-001-01 ...", func(t *testing.T) {...})` |
| xUnit / NUnit | `[Trait("AC", "AC-001-01")]` / `[Category("AC-001-01")]` |
| PHPUnit / Pest | `#[Group('AC-001-01')]` / `it('AC-001-01 ...')` |
| RSpec / Minitest | `it "AC-001-01 ..."` / `test "AC-001-01 ..."` |

## 非機能要件はテストで表現する（P34）
`verify_by: test` の非機能要件は、テスト名/タグに `NFR-xxx-xx` を含める（trace が紐付けを検査）。
- 性能: 代表シナリオの応答時間を計測するテスト（閾値は要件の値、CI では余裕を持たせる）
- 冪等性: 同じリクエストを2回送って結果が1件のテスト
- 同時実行: 並行実行で整合性が崩れないテスト
- 技術方式（依存方向・層構造）はハーネスの検査と任意の ArchUnit 等で表現済み

## ドメインテストの型
- 値: 不変条件の境界（下限-1 / 下限 / 上限 / 上限+1）と等価性を表形式（パラメタライズ）で。
- 区分: 全区分 × 振る舞いを表形式で。
- 状態: 用語集の transitions の**全組み合わせ**（可/不可）を網羅。
- テスト名は業務の言葉。テストを読めば業務ルールが分かること。
