# 02 ドメインモデリング — 業務の言葉を型にする（P05–P13, P23）

`docs/model/domain.yaml` が唯一の正（SSOT）。コードの型名はここの `code_name`（または `code_aliases`）と一致させる（フックが強制）。
初回は `.claude/harness/templates/domain.yaml` をコピーして書き換える。作業は `domain-modeler` サブエージェントに任せてよい。

## 用語ごとに kind を決める
| 業務の言葉の性質 | kind | コードでの形 |
|---|---|---|
| 金額・数量・期間・メールアドレスなど「値」 | value | 不変クラス、完全コンストラクタで検証 |
| 同一性を持ち、時間とともに変化する（注文、会員） | entity / aggregate | identity を持つ。aggregate は整合性の単位 |
| 「〜の一覧」に業務的な意味がある | collection | ファーストクラスコレクション |
| 種類ごとに計算・判断が変わる | kubun | 振る舞いを持つ enum |
| 状態と遷移ルールがある | state | 遷移可否を判断できる enum |
| 名前の付いた判断条件（与信OK、キャンペーン対象） | rule | 仕様オブジェクト |

## 見つけ方（P29）
- **ヒト・モノ・コト**で分類し、`category: hito|mono|koto` を付ける。**コト（取引・約束・出来事）を中心に**業務ルールを集める。
- 各コトに `promises`（約束すること `do` / 約束しないこと `dont`）を書く。約束の範囲を決めることが業務ルールを決めること。
- **重要な部分から**作る。全体を一度に作らず、中核のコトとその周辺から始め、部分と全体を行き来して育てる。
- ドメインオブジェクトを**画面や機能の一部として設計しない**（「注文入力画面用の Order」は作らない）。独立した部品として、複数の機能から組み合わせて使えるように。
- データモデル（テーブルの項目一覧）ではなく**オブジェクトモデル**（振る舞いと関係）で考える。

## 手順
1. 承認済み要件の `business_rules[].terms` をすべて列挙し、1語ずつ定義する（name_ja / code_name / kind / definition）。
2. value には `invariants`（生成時に守る条件）、entity には `identity`、kubun には `values` と `behaviors`、state には `values` と `transitions` を書く。
3. **振る舞い（behaviors）を先に書く**。データ項目の一覧ではなく「このオブジェクトは何ができるか」。計算・判断はそのデータを持つ用語に割り当てる（P04）。
4. 同義語・曖昧語は1つに寄せ、捨てた言い方を `avoid` へ（コードでの悪い名前 `OrderInfo` なども）。
5. `python3 .claude/harness/harness.py trace` でエラー 0 を確認。
6. `design-reviewer` にモデルレビューを依頼。

## 迷ったとき
- サービスクラスに業務ロジックを書きたくなったら（トランザクションスクリプト化）、そのロジックを持つべきドメインオブジェクトが欠けている。用語を足す。
- 基本データ型で済ませたくなったら値オブジェクトにする。後から型を作るより安い。
- 「〜Manager」「〜Info」になりそうなら、業務の人がそれを何と呼ぶか聞く。
- boolean のフラグが2つ以上並ぶなら、区分か状態にまとめられないか検討する。

## 既存コードからの立ち上げ
既存アプリに導入した場合は `python3 .claude/harness/harness.py scaffold-model` で domain の型が `todo: true` 付きで下書き登録される。
コードを読み、ユーザーに業務上の呼び名を確認しながら name_ja / kind / definition を埋め、`todo` を外していく。
コードの名前が業務の言葉とずれていたら、用語集側を正として `code_aliases` に旧名を入れ、リネームを計画する。
