# データベースの設計とドメインオブジェクト（P17 P18 P19 P31）

**業務ロジックはオブジェクトで、事実の記録はテーブルで。** テーブル設計が悪いと、プログラムはその穴埋めで複雑になる。

## 1. 整理に失敗したテーブルの兆候
- 用途がわかりにくいカラム（備考、予備1、区分2、フラグ類）→ lint `sql.vague-column` / `sql.flag`
- いろいろな用途に使う巨大テーブル（NULL だらけ、種別で使うカラムが違う）
- テーブルの関係がわかりにくい（`xxx_id` に外部キーが無い）→ lint `sql.missing-fk`

## 2. 基本を丁寧に実践する
- **NOT NULL**: 全カラム NOT NULL から始める。NULL が必要になったら「その値が無い状態」は別の事実ではないか → 別テーブル。
- **一意性制約**: 業務上の識別子（注文番号、メールアドレス）に UNIQUE。重複データをプログラムで防がない。
- **外部キー**: テーブル間の関係は制約で明示する。
- **CHECK**: 区分・状態・数値範囲の値域を守る。

## 3. コトに注目する
業務アプリケーションの中核は「コト」の記録。ヒト・モノとの関係を正確に記録するための工夫:
1. **記録のタイミングが異なるデータはテーブルを分ける**（注文と出荷と請求は別テーブル。1テーブルに後から埋めるカラムを並べない）
2. **記録の変更を禁止する**（INSERT のみ。訂正は「訂正」というコトを追記、取消は「取消」を追記）
3. **カラム追加ではなくテーブル追加**で拡張する（後から分かる情報は、分かったときのコトとして別テーブルに記録）→ lint `sql.add-column`
4. コトには記録時点の値を持たせる（注文明細に受付時の単価。商品マスタの価格を参照し続けない）

## 4. 状態・残高は導出する
- **UPDATE 文は使わない**（lint `common.sql-update`）。状態は最新の状態変更イベント、残高は入出金の記録から導出する。
- 参照が重いなら、**派生的な情報を転記して作る**（集計テーブル・マテリアライズドビュー・読み取りモデル）。これは導出結果のキャッシュであり、正は元の記録。
- 残高の更新は同時でなくてよい・1か所でなくてよい（締め処理や非同期の集計でよい業務が多い。業務の人に許容範囲を確認する）。

## 5. オブジェクトとテーブル
- 両者は似てくるが**違うもの**。明示的にマッピングする（infrastructure のリポジトリ実装・ORM のマッピング定義）。
- オブジェクトはオブジェクトらしく（振る舞い・値オブジェクト・コレクション）、テーブルはテーブルらしく（正規化・制約・追記）。
- ドメインに ORM のアノテーション・ActiveRecord の継承を持ち込まない（lint が検出）。

## マイグレーションのチェック
- [ ] 新しい事実は新しいテーブルに INSERT で記録している
- [ ] NOT NULL / UNIQUE / FK / CHECK が付いている。NULL 許容には `-- nullable: 理由`
- [ ] 既存データを UPDATE/DELETE/DROP する場合は ADR とロールバック手順がある
- [ ] 状態・残高をどの記録から導出するか design.md に書いた
