# ADR-0009: 画像生成の回数（カウンタ）の UPDATE と、採用されなかった候補の画像の削除を許す

- 状態: 承認（2026-10-04 梶原。REQ-005 の承認とあわせて）
- 日付: 2026-10-04
- 関連: REQ-005（BR-005-07, 11、NFR-005-03）、ADR-0006 / 原則 P18

## 背景
原則 P18 は「上書きより追記、状態は記録から導出」。REQ-005 には、この原則の例外にしたい箇所が2つある。
1. 1日の画像生成の回数を、同時に呼ばれても上限を超えないように確保する（NFR-005-03）
2. 採用されなかった候補の画像を残さない（BR-005-11。2026-10-04 梶原の判断。無料の保存容量 1GB）

## 決定
| 対象 | 許すこと | 理由 |
|---|---|---|
| `image_generation_usage_daily`（テーブル） | count の UPDATE | `INSERT ... ON CONFLICT DO UPDATE ... WHERE count < limit` で原子的に確保するため（ADR-0006 の `llm_usage_daily` と同じ形） |
| Storage `uploads-private/{団体}/candidates/{画像生成ID}/`（ファイル） | 候補の画像の DELETE | 採用の操作を終えた時点で消す。残ったもの（放置）は daily で消す |

- 画像生成と候補の採用の**記録**（`image_generations`・`candidate_adoptions`）は追記のみ。消すのは候補の画像ファイルだけ
- 採用した候補は、画面で投稿画像の形に変換し直して投稿の保存先（`{団体}/posts/…`）に保存するので、候補のフォルダを丸ごと消してよい

## 検討した代替案
- 回数を `image_generations` の件数から数える: 同時に呼ばれたとき上限を超える（数えてから記録するまでに隙間がある）。行ロックで直列化もできるが、ADR-0006 と形をそろえる方が分かりやすい
- 候補の画像を一定期間残す: 後から選び直せるが、保存容量を使い、梶原の判断（すぐ消す）とも違う

## 結果
- ハーネスの lint が UPDATE を指摘した場合は、`image_generation_usage_daily` に限り `harness-allow: P18 ADR-0009` を付ける
- 候補の画像を消したこと自体は記録しない（画像生成の記録と、採用の記録が無いことで十分に追える）
- 片付け（採用の操作を終えた・閉じた）で消せなかった候補は、daily が「画像生成から24時間を過ぎた」ものを消す（選んでいる最中の候補を消さないため）
- カウンタの「日」は SQL で `(now() at time zone 'UTC')::date` と明示し（`current_date` はセッションのタイムゾーンに左右される）、確保と参照の両方で同じ関数（`app.image_generation_day()`）を使う
