## 4. 外部との契約  P20 P21 P33

- 連携方式: いまと同じ（画面 → Supabase の Storage と RPC。管理者の操作）。API関数は使わない（画像の加工は画面で行う。サーバーは保存先・枚数を検査する）。

| 種別 | 名前 | 利用側の関心事 | 入力 → 値オブジェクト変換 | 出力 | エラー |
|---|---|---|---|---|---|
| Storage | `uploads-private/{団体}/style/{uuid}.jpg` に put | 変換した画像を置く | 画面で `ClosingImage.planUpload` を通した JPEG。保存先は `Tenant.closingImagePathFor` | 保存先 | 既存のポリシー（管理者・自分の団体・`style/*.(png\|jpg)`）で拒否。**ポリシーは変えない** |

| テーブルの読み取り | `post_style_closing_images`・`approval_past_posts` | 設定の画像・承認の記録を見たい | — | 行 | RLS（自分の団体のメンバーだけ） |

- 冪等性: 設定の保存は「押すたびに新しい版」でいまと同じ（REQ-002）。Storage の画像は uuid の名前なので、保存に失敗してもファイルが残るだけでどこからも参照されない（背景写真・ロゴと同じ。掃除しない）。
- 後方互換: `save_post_style_settings` は引数が増えるので、**古い署名の関数を drop してから新しい署名で作る**（default 付きの引数を足すと別の関数として共存し、PostgREST が呼び分けに迷うため）。古い画面が名前付きで呼んでも `p_closing_images` を default で受けるので動く（画像0枚の版になる）。**逆に新しい画面は V12 が無いと動かない**（新しいテーブル・引数が無い）ので、7章の順で出す。

## 5. 永続化  P17 P18 P19 P31（/db-design）

| 保存先 | 記録する事実（コト） | 記録のタイミング | 制約 | 欠損を許す項目と理由 |
|---|---|---|---|---|
| `post_style_closing_images`（新規） | 設定の1つの版が持つ最後のスライドの画像（1行＝1枚） | 管理者が設定を保存したとき（`save_post_style_settings` の中） | PK (style_settings_id, position)、`position between 1 and 2`、`unique (style_settings_id, storage_path)`、`storage_path` は1文字以上、FK post_style_settings。**追記のみ**（update/delete を禁じるトリガー。V10 の一覧の作り方に合わせる）。RLS は読むだけ（`app.can_read_style_settings`）、書くのは RPC だけ（画面のロールの書き込み権限を取り消す） | なし（画像が0枚の版は行が無い。ロゴの `post_style_logos` と同じ） |
| `approval_past_posts`（既存） | REQ-007 より前の承認で選んだ過去の投稿 | **新しくは記録しない** | 変更なし | — |

- **連番（間を空けない）** は RPC が配列から 1, 2 と振って入れるので崩れない（制約では書けないため RPC で守る）。
- 状態の導出: 投稿が使う画像は `revision_templates.style_settings_id` → `post_style_closing_images`。承認の記録 `approval_past_posts` があればそちら（`ClosingContent.fromApproval`）。
- **既存の設定の版に画像を後から足さない（マイグレーションでも入れない）**。「記録0件なら設定の画像」で改修前の承認が画像なしになるのは、V12 より前の設定の版に画像の行が無いことによる（用語集の ClosingContent の約束）。AC-007-09 の0件のテストは「V12 前の設定の版＋記録0件」で書く。
- マッピング: TS は `styleRepository.toSettings` で `post_style_closing_images` を読み（`order by position`）、`lib/api/closingSlides.ts` が承認済みの投稿の表示のために最新の承認の `approval_past_posts` を読む。Java は `JdbcTemplateRevisions` の設定の読み取りに足す。
- **マイグレーション V12**（追記型）。順番:
  1. `post_style_closing_images` を作る → 追記のみのトリガー・RLS 有効化・読むポリシー・画面のロールの書き込み権限の取り消し
  2. `drop function public.save_post_style_settings(text, text[], text, text, text, text[], text)` → 新しい署名で作り直す → `revoke execute … from public, anon` → `grant execute … to authenticated`（Supabase の既定で anon にも付くので必ず revoke する）
  3. `create or replace function public.approve_post(...)`（過去の投稿を選ぶ処理を外す）→ **そのあとで** `drop function app.past_post_cover(uuid)`（使う関数を先に置き換える）
  - 既存データ: 既存の設定の版には画像の行を作らない。`approval_past_posts` の行はそのまま（BR-007-05）。
  - ロールバック: V12 を戻すマイグレーションは用意しない（追記型）。7章のとおり、Java だけを戻さない。

## 6. 異常系・外部依存の縮退

| 事象 | 振る舞い | 受入基準 |
|---|---|---|
| アップロードした画像が小さい（切り抜くと 400×500 未満） | 画面が「縦500px・横400px 以上の画像を選んでください」と表示し、その画像を入れない | AC-007-02 |
| PNG・JPEG 以外 | `accept="image/png,image/jpeg"` で選べないようにしたうえで、ドロップなどで渡されたら「PNG か JPEG を選んでください」 | AC-007-03 |
| 画像は読めたがデコードできない（壊れたファイル） | 「画像を読み込めませんでした。PNG か JPEG を選び直してください」と表示し、入れない | AC-007-03 に準じる |
| Storage への put に失敗 | 保存を止めて理由を表示（設定は変わらない）。もう一度「保存」でやり直せる | — |
| 編集者・承認者が保存を要求／他団体のメンバーが読もうとする | RPC が 42501。RLS で他団体の行・Storage の画像は読めない | AC-007-11, NFR-007-02 |
| 画面を通さず 3枚・null・重複・他団体・`.png` などで保存を要求 | RPC が拒否（42501・22023）。新しい版はできない | AC-007-12 |
| 画像化のときに最後のスライドの画像が Storage に無い | 画像化の失敗（内容による失敗。再試行しない）。表示は BR-007-06 の文言だけ（`ClosingContent` が付けた `RenderImageNeed` が「再実行で直らない」ので、`FailureReason` が「今すぐ再実行でやり直せます」を付けない）。ロゴが無いときは今の文言のまま | AC-007-13 |
| 改修前に承認した投稿の画像化（過去の投稿の表紙あり／なし） | 記録のまま描く（`fromApproval`） | AC-007-09 |
| V12 の後、新しい Java が出る前に承認・画像化される | 旧 Java は記録（0件）から画像0枚で描き、作り直されない → 7章の手順（tick を止めてから migrate）で起こさない | — |

## 7. リリースの手順とロールバック

- **デプロイ順**（v0.3.0 と同じ）: ① tick を止める → ② このブランチを ref に指定して migrate（V12）を起動し、適用を確かめる → ③ main に push（Java と画面・Pages のデプロイ）→ ④ 管理者が S-15 で最後のスライドの画像を設定 → ⑤ 進行中の下書きを保存し直す（承認依頼中は修正指示で戻して保存し直す）→ ⑥ tick を有効に戻す。
  - ② と ③ の間に承認されると旧 Java が画像0枚で描くため、tick を止めておく（画像化は tick だけが行う）。新しい画面を V12 より先に出すと S-15・プレビューが壊れるため、② を先にする。
- **ロールバック**: Java・画面だけを戻さない（V12 の後の承認は過去の投稿を記録しないので、旧 Java は画像0枚で描く）。戻すときは、旧 `approve_post`・`app.past_post_cover`・旧署名の `save_post_style_settings` を作り直す V13 と一緒に戻す（新しい表は残してよい）。

## 8. 決定事項（ADR）

ADR は書かない。トレードオフのある判断は次のとおりで、どれも既存の ADR・原則の範囲内:
- テンプレートの版を変えず、最後のスライドの中身の値（`pastPosts` という差し込みの名前）で設定の画像を渡す → ADR-0010 決定1 に沿う。差し込みの名前と業務の言葉がずれるのは niijima@2 を作るときに直す（コメントと用語集に残す）。
- 画像の加工（切り抜き・縮小）を画面で行い、サーバーは画素を検査しない → ロゴ・背景写真と同じ（REQ-002 設計）。Storage に書けるのは自分の団体の管理者だけなので、画面を通さずに大きな画像を置けるのも管理者自身に限られる。
