### シナリオ（P30）

| シナリオ | 手順（使うサービス） | 事前条件 | 結果 |
|---|---|---|---|
| AI の画像で投稿を作る | 投稿作成（S-03）で「AIで作る」→ 画像生成する（S-13）→ 候補を選ぶ → 画面で投稿画像に変換・保存（既存 3.1）。このとき投稿画像に **候補の参照（画像生成ID・位置）と画像の種類**を持たせる → 候補を片付ける → 下書き保存／承認依頼（`save_post_revision` が候補の参照を確かめて候補の採用を記録） | メンバーがログイン済み | 投稿の版に生成画像が入り、候補の採用が記録される。残りの候補は消える |
| 画像生成する（API関数の中） | ①指示の検査（ImagePrompt）→ ②回数の事前確認（読むだけ。上限なら英訳もしない）→ ③LLM利用回数の確保 → 英訳（Gemini、15秒）→ ④画像生成の回数の確保 → ⑤候補を作る（提供元 ×4、残り時間で。全体60秒）→ 候補の画像を保存 → ⑥画像生成を記録 | — | 候補の期限付き URL と回数 |
| 写真風を含む投稿を公開する | （tick）`findForPublishing` が承認された版の投稿画像を生成画像の種類つきで組み立てる → Post が公開内容（公開用キャプション＋AI info を付けるか）を返す → 公開（REQ-001） | 承認済み | 公開。AI info 付き |

- **生成画像であることは、投稿の版の保存と同じ時点で記録・検証する**（レビュー Critical）。画面の手順（変換・アップロード・片付け）の成功には頼らない。切り取る位置を選び直しても、候補の参照は投稿画像に引き継がれる。版の保存に失敗すれば、その画像は投稿に入らない
- 候補の参照は、自団体の成功した画像生成の、候補の数以内の位置であることを RPC が確かめる。参照の無い画像（撮った写真）が生成画像に化けることはない
- ①〜⑥の順番は BR-005-10。②で上限に達していれば、Gemini を呼ばず LLM利用回数も使わない（409）。②と④の間に他の人が使い切った場合は、④で拒否される（このとき LLM利用回数は1回使う）
- ⑤で一部の候補だけ作れたら、ある分だけ返す（1〜3枚）。0枚なら失敗として記録する（AC-005-07）。④で確保した1回は戻さない
- 「どの投稿に採用したか」は、候補の採用の記録（投稿画像に結び付く）から導出する。投稿を一度も保存しなかった候補は採用されなかったことになる

## 2. ドメインモデルの変更  P05–P14 P29

用語は `docs/model/domain.yaml`。置く業務ロジック:

| オブジェクト | 置く業務ロジック | TS（画面・API関数） | Java（定期処理） |
|---|---|---|---|
| `ImagePrompt` | 1〜500文字、メール・電話番号の検出。違反の列挙 | ○ | — |
| `ImageStyle` | 区分ごとの振る舞い（BR-005-01 の表。共通テストケース `fixtures/image-style.json`） | ○ | ○ |
| `ImageGeneration` | 作れた候補の数から結果（成功＝1枚以上／失敗＝0枚）を決める。英訳できなかったときは記録しない（「英訳できた／できなかった」を型で表す） | ○ | — |
| `ImageCandidate` | 画像生成の何番目か（1〜4）、採用されると生成画像になる。**放置の判断**（画像生成から24時間を過ぎた候補は放置とみなして消してよい） | ○ | ○（放置の判断） |
| `GeneratedImage` | 投稿画像が生成画像かどうかと、その画像の種類。AI生成の表示が要るか（種類に委ねる） | ○ | ○ |
| `AiDisclosure` | 投稿の生成画像から、表示が要るか判断。末尾の定型文。is_ai_generated の値 | ○ | ○ |
| `ImageGenerationQuota` / `ImageGenerationUsage` | 上限・警告割合、8割で警告、残り回数 | ○ | — |
| `Post`（TS・Java） | 公開用キャプション = PR表記 + 本文 + AI生成の表示 を**1か所**で組み立てる。上限の判定と拒否の文言も Post が持つ（PrCategory は表記の付け方だけ） | ○ | ○ |

- **公開用キャプションの付記を1か所で組み立てる**。TS は `Post.noticesOf`、Java は `Post.publishContent`。既存の `PrCategory.violationsWithLabel`（TS）と `Post.violationsForPublishing` の「PR表記を含めると」（Java）は Post の付記の判定に移して消す。共通テストケース `fixtures/caption.json` に AI生成の表示のケースを足した（ADR-0005）
- `PostMedia` は「生成画像なら GeneratedImage」を持つ。**編集中**は、候補を採用したときに画面が GeneratedImage を付けた PostMedia を作り、切り取りの選び直し・並べ替えでも引き継ぐ。承認依頼前の文字数検査（AC-005-04, 10）はこの PostMediaList で行う。**復元時**は `post_media_origin`（5章）から付ける
- 提供元の呼び出し口は application のインターフェース（`CandidateImageClient`）。用語集の `ImageGenerator` は「提供元とモデル名の組（設定値）」のまま（レビュー指摘。1つの名前に2つの責務を乗せない）
- LLM利用回数（`LlmUsage`）は REQ-002 の用語。REQ-005 では確保と上限の判定だけを、01_DB設計の `try_consume_llm`（太平洋時間の日、上限は `tenant_settings_current.llm_daily_limit`）として作る。警告・手動コピペ・英訳用プロンプトの版管理は REQ-002 で足す（申し送り）
- PR入稿の入稿者連絡先の検査（BR-005-06 の一部）は、PR入稿（REQ-003）ができるまで成り立たない（PR入稿由来の投稿が無い）。REQ-003 の設計で、画像生成の入力に投稿の文脈を足して検査する（申し送り）

## 3. 画面  P32（/ui-design）

| 画面（タスク） | 利用者の関心事 | 表示するドメインオブジェクト | 項目の並び・グルーピング | 状態ごとの見せ方（ドメインが返す） |
|---|---|---|---|---|
| S-03 投稿を作る（変更） | 画像の入口を増やす | PostMediaList | 画像の入口を「写真を撮る」「写真を選ぶ」「AIで作る」の3つにする | 残り枚数が0なら入口を出さない |
| S-13 画像を生成する（新規。S-03 から開く全画面のシート） | 撮れない話題の画像をすぐ手に入れる | ImageStyle, ImagePrompt, ImageGenerationUsage, ImageCandidate | ①画像の種類（セグメント）②指示（1〜500文字・残り文字数）③今日の残り回数 ④「生成」⑤候補（2×2。タップで選択、複数可）⑥「選んだ画像を使う」／左上「キャンセル」 | 写真風なら注意書き（AC-005-09）。上限の8割で注意、上限なら「生成」を出さず案内（AC-005-06）。生成中は進み具合（〜30秒） |
| S-04 投稿詳細（変更） | 写真風の生成画像を確かめて承認する | Post, GeneratedImage | 承認待ちで写真風の生成画像を含むとき、状態の下に確認表示（AC-005-08） | 背景・イラストだけなら出さない |
| S-02 ホーム（変更） | 回数の上限に気づく | Alert | 警告バナーに IMAGE_LIMIT_NEAR / REACHED を足す | — |

- 候補は 1024×1024 の正方形で返る。「選んだ画像を使う」で、画面が既存の変換で 4:5（カルーセルの2枚目以降は1枚目の比率）に切り取り、投稿の保存先（`{団体}/posts/`）にアップロードし、**候補の参照（GeneratedImage）を付けた PostMedia** を投稿画像一覧に加える。そのあと「候補を片付ける」を呼ぶ（失敗しても daily が消す）
- 切り取る位置の選び直しは、元の候補画像を保持している間だけ。選び直した PostMedia にも同じ GeneratedImage を引き継ぐ
- キャンセル・画面を閉じたときも「候補を片付ける」を呼ぶ（BR-005-11）。作成中の投稿の内容（ほかの画像・キャプション）は変えない（AC-005-07）

## 4. 外部との契約（API / CLI / メッセージ）  P20 P21 P33

- 連携方式: 画面 → API関数（Web API。鍵をブラウザに出さないため。NFR-005-01）。API関数 → Gemini（REST、`GEMINI_API_KEY`）、→ Workers AI（AI バインディング。ADR-0008）、→ Supabase（service role の RPC・Storage）。候補の採用は画面 → RPC（`save_post_revision`）
- 認証: REQ-001 と同じ（`Authorization: Bearer <Supabase のアクセストークン>` → `member_current`）。エラー形式も共通

| 種別 | 名前 | 利用側の関心事 | 入力 → 値オブジェクト変換 | 出力 | エラー |
|---|---|---|---|---|---|
| Web API | `POST /api/image-generations` | 候補がほしい | `{ style, prompt }` → `ImageStyle`, `ImagePrompt` | 201 `{ generationId, candidates: [{ position, url }], usage: { used, dailyLimit, warnRatio } }`（url は期限付き 1時間） | 400 INVALID_PROMPT（`details` に違反）／403 FORBIDDEN／409 IMAGE_LIMIT_REACHED／503 TRANSLATION_UNAVAILABLE（LLM上限・Gemini の失敗・15秒超過）／502 GENERATION_FAILED（提供元の失敗・0枚）／504 GENERATION_TIMEOUT（全体60秒） |
| Web API | `POST /api/image-generations/{id}/clear` | 候補を消す | — | 204（何度呼んでもよい） | 403（他団体）／404 |
| RPC（画面） | `save_post_revision(post, revision)`（拡張） | 下書きを保存（候補の採用を含む） | media 要素に任意で `generation: { generationId, candidatePosition }` | `{ post_id, revision_id }` | 22023（候補の参照が不正）／REQ-001 と同じ |
| RPC（画面） | `image_generation_usage()` | 今日の残り回数 | — | `{ used, daily_limit, warn_ratio }`（生データ。判断は画面の ImageGenerationUsage） | 42501 |
| RPC（service role） | `try_consume_image_generation(tenant, limit)` / `try_consume_llm(tenant, model, limit)` | 1回分を原子的に確保 | — | `{ allowed, used }` | — |
| RPC（service role） | `record_image_generation(...)` | 記録 | — | — | — |
| Graph API | `POST /{ig-user-id}/media` | AI info を付ける | `is_ai_generated=true`（写真風を含むとき。画像は単体、カルーセルは親コンテナ） | — | REQ-001 と同じ |

- 回数は POST の結果も RPC も生データ（used・上限・警告割合）で返し、判断は画面の `ImageGenerationUsage` に置く（形をそろえる）
- 冪等性: 画像生成は呼ぶたびに別の画像生成（回数を使う）。片付けは何度呼んでもよい
- 投稿画像の保存先は `{団体}/posts/` に限る（`save_post_revision` と Storage の insert ポリシーの両方で。候補の保存先 `candidates/` はメンバーが書けない）

## 5. 永続化  P17 P18 P19 P31（V8 マイグレーション）

| 保存先 | 記録する事実（コト） | 記録のタイミング | 制約 | 欠損を許す項目と理由 |
|---|---|---|---|---|
| `image_generation_settings` | 画像生成の設定の版（提供元・モデル・上限・警告割合） | 設定変更時（初版は V8・初期データ） | (tenant, version) 一意、上限 ≥1、0<警告割合≤1 | created_by（初版は SQL で登録） |
| `image_generations` | 画像生成した | 提供元を呼んだ後（成功・失敗とも） | style・outcome の CHECK、指示 1〜500文字、候補数 0〜4、成功なら 1 以上 | なし（英訳できなかったときは記録しない） |
| `candidate_adoptions` | 候補を投稿の版に入れた（候補の採用） | 版の保存時（`post_media` と同じ時点・同じ RPC） | post_media_id 主キー、位置 1〜4、画像生成は自団体の成功したもの・候補の数以内（RPC で検査） | なし |
| `image_generation_usage_daily` | 日ごとの画像生成の回数（カウンタ。ADR-0009） | 確保時 | (tenant, 日) 主キー、count ≥0 | なし |
| `llm_usage_daily` | 日ごとの LLM 呼び出し回数（01_DB設計の設計どおり。ADR-0006） | 英訳の直前 | (tenant, 日, モデル) 主キー | なし |
| Storage `uploads-private/{団体}/candidates/{画像生成ID}/{位置}.jpg` | 候補の画像（一時） | 画像生成時 | service role だけが書く | — （片付け・daily で消す。ADR-0009） |

- **生成画像かどうかは導出**する。`post_media_origin` ビュー = `post_media` ⟕ `candidate_adoptions`（post_media_id）⟕ `image_generations`（画像の種類）
- 版を作り直す（下書きの再保存）たびに、生成画像の投稿画像には新しい `candidate_adoptions` の行ができる（同じ候補が複数の版に入る）。「いつ最初に採用したか」は最初の行で分かる
- 日の区切り: 画像生成は UTC の日付（= 日本時間 9:00）、LLM は太平洋時間の日付。どちらも確保と参照で同じ SQL 関数（`app.image_generation_day()` / `app.llm_day()`）を使う
- 画面から読めるのは自団体の記録と回数（RLS）。書くのは RPC だけ
- マイグレーション: V8 で追加。`save_post_revision` を置き換える（候補の参照・保存先 `posts/` の検査）。Storage の insert ポリシーを `{団体}/posts/` に限る。初期データとして既存の団体に `image_generation_settings` の版1（Workers AI / flux-1-schnell / 20回 / 0.8）を入れる。`scripts/seed_tenant.sql` にも足す

## 8. 決定事項（ADR）

- ADR-0008 画像生成は Workers AI の FLUX.1 [schnell] を API関数の AI バインディングで呼ぶ。指示は Gemini で英訳する
- ADR-0009 画像生成の回数の UPDATE と、採用されなかった候補の画像の削除を許す
- ADR-0005 TS と Java の二重実装（AiDisclosure・ImageStyle・GeneratedImage・公開用キャプションを共通 fixtures に）
- ADR-0006 `llm_usage_daily` の UPDATE（REQ-002 の設計を前倒しで作る。2026-10-04 承認済み）
