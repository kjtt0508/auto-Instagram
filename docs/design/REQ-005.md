# REQ-005 設計: AIで投稿画像（背景・イラスト・写真風）を生成する

> 「コードを読めば分かること」は書かない。判断・契約・境界だけを書く。
> 前提: REQ-001 の設計（投稿・画像の変換・API関数・RPC）、ADR-0008（提供元）、ADR-0009（カウンタと候補の削除）

## 1. ユースケース（アプリケーション層）  P15

| 候補を採用する（残りを消す） | 更新 | 画面 → API関数 | `CandidateAdopting.adopt`（`POST /api/image-generations/{id}/adoptions`） | ImageCandidate, CandidateAdoption, PostMediaList |

### シナリオ（P30）

| シナリオ | 手順（使うサービス） | 事前条件 | 結果 |
|---|---|---|---|
| AI の画像で投稿を作る | 投稿作成（S-03）で「AIで作る」→ 画像生成する（S-13）→ 候補を選ぶ → 画面で投稿画像に変換・保存（既存 3.1）→ 候補を採用する → 下書き保存／承認依頼（REQ-001） | メンバーがログイン済み | 投稿画像一覧に生成画像が加わる。残りの候補は消える |
| 画像生成する（API関数の中） | ①指示の検査（ImagePrompt）→ ②LLM利用回数の確保 → 英訳（Gemini）→ ③画像生成の回数の確保 → ④候補を作る（ImageGenerator ×4）→ 候補の画像を保存 → ⑤画像生成を記録 | — | 候補の期限付き URL と回数 |
| 写真風を含む投稿を公開する | （tick）PostPublishing が承認された版の生成画像の種類を読む → AiDisclosure がキャプション末尾の表示と is_ai_generated を決める → 公開（REQ-001） | 承認済み | 公開。AI info 付き |

- ①〜⑤の順番は BR-005-10。英訳できない（LLM上限・Gemini の失敗）なら ③ に進まない（画像生成の回数を使わず、記録もしない）
- ④で一部の候補だけ作れたら、ある分だけ返す（1〜3枚）。0枚なら失敗として記録する（AC-005-07）。③で確保した1回は戻さない（提供元の無料枠を使ったため）

## 2. ドメインモデルの変更  P05–P14 P29

用語は `docs/model/domain.yaml`（2026-10-02 登録）。置く業務ロジック:

| オブジェクト | 置く業務ロジック | TS（画面・API関数） | Java（定期処理） |
|---|---|---|---|
| `ImagePrompt` | 1〜500文字、メール・電話番号の検出（個人を特定できる情報）。違反の列挙 | ○ | — |
| `ImageStyle` | 区分ごとの振る舞い（注意書き・承認時の確認・AI生成の表示・is_ai_generated）。BR-005-01 の表 | ○ | ○ |
| `GeneratedImage` | 投稿画像が生成画像かどうかと、その画像の種類。AI生成の表示が要るか（種類に委ねる） | ○ | ○ |
| `AiDisclosure` | 投稿の生成画像から、表示が要るか判断。公開用キャプションの末尾に定型文を付ける。is_ai_generated の値 | ○ | ○ |
| `ImageGenerationQuota` / `ImageGenerationUsage` | 上限・警告割合、8割で警告 | ○ | — |
| `ImageCandidate` | 画像生成の何番目か（1〜4） | ○ | — |
| `Post`（TS・Java） | `violationsBeforeApprovalRequest` に AI生成の表示込みの文字数を加える。公開用キャプション = PR表記 + 本文 + AI生成の表示 を**1か所**で組み立てる（`Post.publishCaption`） | ○ | ○ |

- **公開用キャプションの付記を1か所で組み立てる**（REQ-005 レビュー指摘）。`Post.publishCaption(prLabel)` が PR区分（先頭）と AiDisclosure（末尾）を順に適用する。拒否文言は付けた付記の名前で組み立てる（「PR表記とAI生成の表示を含めて2,200文字以内にしてください」）。TS と Java の共通テストケースに AI生成の表示のケースを足す（ADR-0005。`docs/model/fixtures/caption.json`）
- `PostMedia` は「生成画像なら画像の種類」を持つ（`GeneratedImage` を任意で持つ）。復元時に `post_media_origin` ビュー（5章）から読む
- LLM利用回数（`LlmUsage`）は REQ-002 の用語。REQ-005 では確保と上限の判定だけ作る（警告・手動コピペは REQ-002）

## 3. 画面  P32（/ui-design）

| 画面（タスク） | 利用者の関心事 | 表示するドメインオブジェクト | 項目の並び・グルーピング | 状態ごとの見せ方（ドメインが返す） |
|---|---|---|---|---|
| S-03 投稿を作る（変更） | 画像の入口を増やす | PostMediaList | 画像の入口を「写真を撮る」「写真を選ぶ」「AIで作る」の3つにする | 「AIで作る」は残り枚数が0なら出さない |
| S-13 画像を生成する（新規。S-03 から開く全画面のシート） | 撮れない話題の画像をすぐ手に入れる | ImageStyle, ImagePrompt, ImageGenerationUsage, ImageCandidate | ①画像の種類（セグメント）②指示（1〜500文字・残り文字数）③今日の残り回数 ④「生成」⑤候補（2×2。タップで選択、複数可）⑥「選んだ画像を使う」／左上「キャンセル」 | 写真風なら注意書き（AC-005-09）。上限の8割で注意、上限なら「生成」を出さず案内（AC-005-06）。生成中は進み具合（〜30秒） |
| S-04 投稿詳細（変更） | 写真風の生成画像を確かめて承認する | Post, GeneratedImage | 承認待ちで写真風の生成画像を含むとき、状態の下に確認表示（AC-005-08） | 背景・イラストだけなら出さない |
| S-02 ホーム（変更） | 回数の上限に気づく | Alert | 警告バナーに IMAGE_LIMIT_NEAR / REACHED を足す | — |

- 候補は 1024×1024 の正方形で返る。「選んだ画像を使う」で、画面が既存の変換（`convertForInstagram`）で 4:5（カルーセルの2枚目以降は1枚目の比率）に切り取り、投稿の保存先にアップロードしてから「候補を採用する」を呼ぶ。切り取る位置は既存の「切り取る位置」で選び直せる（元の候補画像を保持している間）
- キャンセル・画面を閉じたときも「候補を採用する」を空の採用で呼び、候補を消す（BR-005-11）。呼べずに終わったものは daily が消す

## 4. 外部との契約（API / CLI / メッセージ）  P20 P21 P33

- 連携方式: 画面 → API関数（Web API。鍵をブラウザに出さないため。NFR-005-01）。API関数 → Gemini（REST、`GEMINI_API_KEY`）、→ Workers AI（AI バインディング。ADR-0008）、→ Supabase（service role の RPC・Storage）
- 認証: REQ-001 と同じ（`Authorization: Bearer <Supabase のアクセストークン>` → `member_current`）。エラー形式も共通

| 種別 | 名前 | 利用側の関心事 | 入力 → 値オブジェクト変換 | 出力 | エラー |
|---|---|---|---|---|---|
| Web API | `POST /api/image-generations` | 候補がほしい | `{ style, prompt }` → `ImageStyle`, `ImagePrompt` | 201 `{ generationId, candidates: [{ position, url }], usage: { used, limit, nearLimit } }`（url は期限付き 1時間） | 400 INVALID_PROMPT（文字数・個人情報。`details` に違反）／403 FORBIDDEN／409 IMAGE_LIMIT_REACHED／503 TRANSLATION_UNAVAILABLE（LLM上限・Gemini の失敗）／502 GENERATION_FAILED（提供元の失敗・0枚）／504 GENERATION_TIMEOUT（60秒） |
| Web API | `POST /api/image-generations/{id}/adoptions` | 選んだ候補を使う（残りを消す） | `{ adopted: [{ position, storagePath }] }`（空なら採用なし）→ `ImageCandidate`、保存先は自団体の `posts/` であること | 204 | 400（位置が範囲外・保存先が他団体）／403（他人の画像生成）／404 |
| RPC（画面） | `image_generation_usage()` | 今日の残り回数 | — | `{ used, limit, warn_ratio }` | 42501 |
| RPC（service role） | `reserve_image_generation(tenant, limit)` / `reserve_llm_usage(tenant, model, limit)` | 1回分を原子的に確保 | — | `{ allowed, used }` | — |
| RPC（service role） | `record_image_generation(...)` / `record_candidate_adoptions(...)` | 記録 | — | — | — |
| Graph API | `POST /{ig-user-id}/media` | AI info を付ける | `is_ai_generated=true`（写真風を含むとき。画像は単体、カルーセルは親コンテナ） | — | REQ-001 と同じ |

- 冪等性: 画像生成は呼ぶたびに別の画像生成（回数を使う）。採用は同じ `(画像生成, 位置)` を2回記録しない（一意制約）。2回目の採用呼び出しは記録済みを無視して 204
- バージョニング: 利用側は自前の画面だけ。URL にバージョンを入れず後方互換を保つ（REQ-001 と同じ）

## 5. 永続化  P17 P18 P19 P31（V8 マイグレーション）

| 保存先 | 記録する事実（コト） | 記録のタイミング | 制約 | 欠損を許す項目と理由 |
|---|---|---|---|---|
| `image_generation_settings` | 画像生成の設定の版（提供元・モデル・上限・警告割合） | 設定変更時（初版は V8 の初期データ） | (tenant, version) 一意、上限 ≥1、0<警告割合≤1 | なし |
| `image_generations` | 画像生成した | 提供元を呼んだ後（成功・失敗とも） | style・outcome の CHECK、指示 1〜500文字、候補数 0〜4、成功なら 1 以上 | なし（英訳できなかったときは記録しない） |
| `candidate_adoptions` | 候補を採用した | 採用時 | (画像生成, 位置) 一意、保存先一意、位置 1〜4 | なし |
| `image_generation_usage_daily` | 日ごとの画像生成の回数（カウンタ。ADR-0009） | 確保時 | (tenant, 日) 主キー、count ≥0 | なし |
| `llm_usage_daily` | 日ごとの LLM 呼び出し回数（01_DB設計の設計どおり。ADR-0006） | 英訳の直前 | (tenant, 日, モデル) 主キー | なし |
| Storage `uploads-private/{団体}/candidates/{画像生成ID}/{位置}.jpg` | 候補の画像（一時） | 画像生成時 | service role だけが書く | — （採用の操作の後・翌日の daily で消す。ADR-0009） |

- **生成画像かどうかは導出**する。`post_media_origin` ビュー = `post_media` ⟕ `candidate_adoptions`（保存先で結合）⟕ `image_generations`（画像の種類）。投稿画像に「生成画像か」のカラムは足さない（記録のタイミングが違う事実を混ぜない。P31）
- 画像生成の回数の「日」は UTC の日付（= 日本時間 9:00 区切り。Workers AI の無料枠のリセットに合わせる。BR-005-07）
- 画面から読めるのは自団体の `image_generations`・`candidate_adoptions`・回数（RLS）。書くのは API関数（service role）の RPC だけ
- マイグレーション: V8 で追加のみ。初期データとして既存の団体に `image_generation_settings` の版1（Workers AI / flux-1-schnell / 20回 / 0.8）を入れる

| 事象 | 振る舞い | 受入基準 |

## 8. 決定事項（ADR）

- ADR-0008 画像生成は Workers AI の FLUX.1 [schnell] を API関数の AI バインディングで呼ぶ。指示は Gemini で英訳する
- ADR-0009 画像生成の回数の UPDATE と、採用されなかった候補の画像の削除を許す
- ADR-0005 TS と Java の二重実装（AiDisclosure・公開用キャプションを共通 fixtures に足す）
- ADR-0006 `llm_usage_daily` の UPDATE（REQ-002 の設計を前倒しで作る）
