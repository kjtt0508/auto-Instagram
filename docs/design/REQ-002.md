**公開用キャプションの組み立て（TS・Java で完全に同じ。caption.json に完全な期待文字列を持つ）**

```text
[PR表記（PR案件のみ。団体設定の prLabel をそのまま。改行を含む）]
+ キャプション
+ ["\n" + AI生成の表示の定型文]                         （要るときのみ）
+ ["\n\n" + キャプションの定型]                          （テンプレートの投稿のみ）
+ ["\n\n" + ハッシュタグを "\n" でつないだもの]          （テンプレートの投稿のみ。固定 → 追加、重複は除く）
```

- アップロードの投稿は、これまでの `Post.noticesOf` / `notices` と完全に同じ文字列になる（既存ケースに完全な期待文字列を足して確かめる。中断した公開の復旧で同じキャプションになること＝AC-005-11 を守る）。
- 違反の説明: 付けた「PR表記」「AI生成の表示」の名前をこの順に「と」でつなぐ（例「PR表記とAI生成の表示を含めて2,200文字以内にしてください（2,201文字）」= AC-002-18）。どちらも無いテンプレートの投稿は「キャプションの定型とハッシュタグを含めて…」。キャプションの定型とハッシュタグは名前に出さないが文字数には数える。
- キャプションにハッシュタグが混ざっても拒否しない（30個の上限には数える）。

**修正指示の取り込み（`SlideList.withDraftText`）**
- REVISE は中のスライドの枚数を入力と同じに固定する（スキーマで枚数を指定し、違えば違反）。位置ごとに文言・絵の指示だけを差し替え、素材画像は保つ。
- 表紙の背景写真は修正では変えない（AI が背景写真を選ぶのは最初の生成だけ。以後は人が選び直す）。
- 帯の色・表紙の文言は修正で変わってよい。

**移行（REQ-005 からの変更。単位1で TS・Java を同時に直す）**
- `Post.noticesOf`（TS）/`Post.notices`（Java）を `PublishCaption` に置き換える。
- `AiDisclosure.of(PostMediaList)` を `AiDisclosure.of(PostRevision)` にする（投稿画像一覧かスライド構成に問い合わせる）。
- 公開の検査 `Post.violationsForPublishing` は、投稿画像一覧の枚数ではなく `PostRevision.expectedPublishMediaCount()` と準備済みの枚数を比べる。テンプレートの投稿の ImageSpec の検査は、画像化した JPEG に対して行う（単位3）。

**プレビュー（ADR-0010）**
- `<iframe sandbox="allow-scripts" src="/templates/<版>/index.html">`（`allow-same-origin` なし＝opaque origin）。データは `postMessage` で渡し、テンプレート側は `event.source === window.parent` を確かめてから `render(data)` する。**srcdoc に JSON を埋め込まない**（`</script>` で抜け出せるため）。
- テンプレートは `<meta http-equiv="Content-Security-Policy" content="default-src 'none'; script-src 'self'; style-src 'self'; font-src 'self'; img-src data: blob:">` を持つ。画像は data URL / blob で渡す。

- 参照元 URL（`sourceUrls`）は REQ-002 では投稿の版に記録しない（下書き案の検査と、修正での保持だけ）。版に持たせて公開前に確かめるのは REQ-003 で扱う。
- 応答の `unsupportedFacts` は画面では使わない。編集中の文言に追従させるため、画面が `unsupportedFactsInWork`（ネタと今の文言から）で計算し直す。API が返す値は、生成した時点の記録と他の利用側のためのもの。
- 他団体の generation・idea・プロンプト版は、存在を知らせないよう「無い」と同じ 404 にそろえる（403 はメンバーでないときだけ）。
- `current` は `DraftProposal.readCurrent` で下書き案と同じ形・同じ検査（形・中のスライドの枚数・PR区分）に通す。知らない欄は捨て、下書き案の形に整えたものだけをプロンプトと `generations.input` に入れる。文字数の違反は受け付ける（画面で赤字のままでも作り直せる）。JSON で 32,768 文字を超える巨大な値は 400 INVALID_REQUEST。

- 投稿の型の設定の版は、画面から受け取らず **DB が保存時点の現在の版** を記録する。
- テンプレートの版は、V10 の `template_releases`（版の名前の一覧。新しい版を足すときはマイグレーションで行を足す）と照合する。存在しない版は 22023。

**Gemini**
- `generateContent` に `responseMimeType=application/json` と `responseSchema`（下書き案の形。REVISE は中のスライドの枚数を入力に合わせた形）を渡す。入力は `GenerationInput` だけ（AC-002-09 は、組み立てた入力をシリアライズして入稿者連絡先の欄が無いことを確かめる）。

## 6. 公開用画像の準備（PREPARE_MEDIA）

```text
MediaPreparation:
  revision = 承認された投稿の版
  revision.preparation() が
    複製（UPLOAD）   → これまでどおり publish_media へ
    画像化（TEMPLATE）→ 下記

画像化:
  approval = 最新の承認の出来事、pastPosts = approval_past_posts
  refs = revision.imageRefs() + pastPosts の表紙 → Storage から読む（無ければ RENDER_FAILED）
  browser = Playwright for Java の chromium（tick で1回だけ起動）
  page.route("https://template.local/**") → templates/<版>/ のファイルを返す。それ以外はすべて abort
  for slide in revision.slides:
    page.navigate("https://template.local/<版>/index.html")
    page.evaluate("data => window.render(data)", slideJson + settingsJson + 画像の data URL)   // フォントと全画像の decode を待つ Promise
    screenshot(JPEG, 1080×1350, quality 90) → ImageSpec.check
    → uploads-private/{団体}/renders/{承認}/{順番}.jpg → template_renders → media-public へ複製 → template_publish_media
```

- **失敗したとき**: 失敗は2つに分ける。
  - 内容による失敗（画像が無い・描画の例外・ImageSpec 違反）は、その場で投稿を失敗（RENDER_FAILED）にする。予約中から失敗への出来事は post_failures に記録し、ジョブを FAILED で終える（出来事を作ってよいのは予約中だけ。`Post.failedPreparing`）。続く公開ジョブは投稿が予約中でないので何もしない（REQ-001 の Skip）。
  - 一時的な失敗（Playwright の起動失敗・描画中のブラウザの切断・Storage の 5xx や接続失敗・公開用への複製の失敗・記録の RPC の例外）は `RenderTemporaryFailureException` にし、ジョブを次の tick で再試行する（最大3回）。3回目も失敗したら RENDER_FAILED にする。どちらもジョブを RUNNING のまま残さない（tick の runSafely に落とさない）。写真の投稿の複製の失敗の扱いは従来どおり。
- 承認の出来事は、承認された版（`approvedRevisionId`）を承認した最新の出来事を引く（投稿 ID だけで引かない）。`record_template_render` も `p_revision` を受け取り、承認の出来事の版と照合する。読んだあとに再承認されていたら、記録せずにジョブを再試行する。
- 公開用の保存先（media-public）は、承認と順番から決まる名前（HMAC(HMAC(service role キー, "media-public-name"), 団体/render/承認/順番)。用途ラベルで鍵を派生させる）にして、再試行で孤児を作らない。複製先が既にあれば成功として扱う。service role キーを変えても公開は壊れない: 公開済みの画像の保存先は `template_publish_media` にパスごと記録してあり、記録済みの順番は名前を作り直さない（変わるのは、キー変更後に新しく複製する分の名前だけ）。
- **tick の持ち時間**: 画像化が長引いても写真の投稿の公開が動くよう、準備は「ジョブ開始から 8 分 30 秒（timeout-minutes 10 分 − 余裕 90 秒）− 公開の 2 分」で打ち切る。tick.yml の最初の手順でジョブの開始時刻を記録して Java に渡し（`--workflow-started-at`）、ブラウザの導入にかかった時間も差し引く。画像化はスライドの間で残り時間を確かめ、足りなければ一時的な失敗（TIME_BUDGET。描けた分は記録済みで、次の tick で続きから）にする。1 枚の描画は `waitForFunction` の 30 秒で打ち切る。
- 画像（data URL）は、スライドごとに必要な参照だけを渡す（表紙は背景写真、中は素材画像、最後は過去の投稿の表紙とロゴ）。
- 公開の検査は `PostRevision.expectedPublishMediaCount()` と準備済みの枚数を比べる（2章の移行）。準備が済んだか（`Post.isPreparedWith`）は投稿が決め、足りないときは MEDIA_REJECTED にせず準備を待つ（`MEDIA_NOT_PREPARED`、ジョブの再試行）。
- 写真の投稿の公開用画像は `publish_media` だけを読む。`template_publish_media` はテンプレートの投稿の版のときだけ読む（V10 の前でも写真の投稿が止まらない）。
- **リリース手順: V10 を含むブランチ（例 `release/req-002`）を push → そのブランチを ref に指定して migrate（V10）を起動・承認 → `flyway_schema_history` に v10 があることを確かめる → main に push → Cloudflare Pages にデプロイ → tick を有効に戻す**。migrate は起動したブランチのコードを使うので、main から起動すると V10 が入っていない（2026-10-09 最終レビュー）。tick は止めたまま migrate する（`post_failures` の CHECK の付け替えが一瞬ロックを取る。daily の 4:00 とも時間をずらす）。この順番を守る。V10 を本番に流す前にこのコードが tick で動くと、`template_publish_media` が無く、テンプレートの投稿の準備が SQL エラーになる（写真の投稿は上の分離で影響を受けない）。
- tick.yml の chromium の導入は外部の都合（配布元・apt）で失敗しても、tick を止めない（`continue-on-error`）。画像化のコードはブラウザの自動ダウンロードを止めている（`PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD`）。入っていなければ起動に失敗し、一時的な失敗として再試行される。
- テンプレートとフォント（Noto Sans JP・Noto Color Emoji）は `templates/<版>/` の中に置き、版ごとにファイルのハッシュを固定するテストを持つ。古い版は、その版を使う投稿がある限り消さない（実質的に消さない）。
- 画面のビルドで `templates/` を静的出力の `/templates/` にコピーする。GitHub Actions の tick に Playwright の chromium を入れる（キャッシュする）。
