**`BackgroundPhotoAdopting.adopt` の順番（API関数）**: ① メンバーを確かめる（全ロール）→ ② 説明文の形を `BackgroundPhoto` で検査 → ③ service role で画像生成を読み、自団体・成功・位置が候補の数以内・画像の種類が ILLUSTRATION かを確かめる（満たさなければ 404 / 409 NOT_ADOPTABLE）→ ④ すでに同じ候補の採用の記録があれば、その背景写真を **200** で返して終わる（応答が失われた再試行の救済。**ただしその背景写真が「使わない」なら 409 NOT_ADOPTABLE**。RPC と同じ）→ ⑤ Storage に候補の画像（`{団体}/candidates/{画像生成ID}/{位置}.jpg`）があるか確かめる（無ければ 409 CANDIDATE_GONE）→ ⑥ 候補を `{団体}/backgrounds/{uuid}.jpg` に**複製**する（サーバーは画像を加工しない。`backgrounds/` は管理者だけが書ける保存先だが、service role で書く）→ ⑦ `record_generated_background` を呼ぶ → ⑧ ⑦が**確定した拒否**（SQLSTATE が分かる）で失敗したら、⑥で複製した画像を消して失敗を返す（孤児を残さない）。**結果が分からない失敗**（接続の失敗・応答の消失・時間切れ）では、DB が記録済みかもしれないので複製を消さず、採用の記録を読んで確かめる（記録があれば成功として返す／無ければ複製を消して失敗／確かめる読み取りも失敗したら複製を消さず 502。6章）。

- 背景写真の保存先は `backgrounds/` のままなので、**Storage のポリシーも `register_background_photo` も変えない**。メンバーが書ける保存先（`posts/`）を背景に使わず、画面が渡した画像を信用しない（編集者が実物の写真や写真風の画像を「AI が作った背景」として共有の背景写真に混ぜられない）。
- `record_generated_background` は、団体の `tenants` を `for no key update` で直列化 → メンバーが有効か（`member_current.active`。無効化されたメンバーは P0404）→ **そのあとで**二重採用（`unique (generation_id, candidate_position)` に当たる前に調べる。当たったら既存の背景写真IDを返す。**ただしその背景写真が「使わない」なら返さず 22023「この背景は使わない設定になっています」で拒否**する）→ 使う背景写真が30枚未満か（`register_background_photo` と同じ数え方。NFR-006-04。**満たさなければ P0409**）→ 画像の種類・採用できる候補（`app.require_adoptable_candidate` と同じ条件）→ 説明文 → 保存先の形 → `background_photos` と `background_photo_adoptions` を1つのトランザクションで追記（`storage_path unique` の違反は 22023 にする）。
- **説明文の境界は TS と RPC でそろえる**: 改行・制御文字・U+2028/2029 を含まないこと（`app.is_background_description(text)`。DB の置き場所は1つ）を先に検査し、そのあとで**前後の空白を取り除いて** 1〜100文字を数え、**取り除いた値を保存**する（TS の `BackgroundPhoto.violationsOfDescription` が trim してから数えるのと同じ。先頭に空白1つ＋100文字は両方とも受け付け、空白だけは両方とも拒否）。`register_background_photo`（V10・管理者の登録）は変えない。
- **記録から戻すとき（TS の `BackgroundPhoto.restore`）は説明文を検査しない**（過去に登録された写真が読み込みで落ちないように。`CoverText` と同じ方針）。`origin` は必須で、`usable_background_photos.generated` を読んで渡す。
- 画像化（Java）は、背景写真の保存先を読むだけなので変更しない。見つからなければ RENDER_FAILED（AC-006-14）。

| 権限・RLS（V10 と同じ手順を V11 に書く） | `background_photo_adoptions`: RLS を有効にし、同団体のメンバーが読める（背景写真の団体で判定。`app.can_read_background_photo` を使う）。更新・削除は追記のみのトリガーで禁止。`authenticated`・`anon` からの insert/update/delete を revoke。`record_generated_background` は `revoke … from public, anon, authenticated`・`grant … to service_role`（V8 の `record_image_generation` と同じ）。V10 の一覧は変えず、V11 に同じループを書く |

- `background_photos` に **origin の列は足さない**（出どころは採用の記録から導く。食い違いを作らない。P31）。
- DB は形と団体の境界だけを検査し、画像の種類・30枚などの判断は RPC とドメインが持つ（ADR-0005。30枚は同時実行のため RPC で検査する。REQ-002 と同じ）。
- Storage のポリシーは変えない。

## 9. リリース手順

REQ-002 設計 6章の手順と同じ（V11 を含むブランチ `release/req-006` を push → そのブランチを ref に migrate を起動・承認 → `flyway_schema_history` に v11 があることを確認 → main に push → Cloudflare Pages にデプロイ）。V11 は表・列・制約・関数の追加だけで、tick を止める必要はない（tick・daily は Meta の準備ができるまで無効のまま）。

- **migrate 後の確認**: `record_generated_background` を呼んで 404 になるときは、PostgREST のスキーマキャッシュが古い。SQL で `notify pgrst, 'reload schema'` を実行してから確かめる。
- **デプロイ後に本番で1回確かめる**: 背景を AI で作って採用し、背景写真が1枚増えること、Storage の `backgrounds/` にその画像があることを確かめる（Storage の `object/info`・`object/copy` は偽物でしか確かめていないため）。
- **戻すときの注意**: 新しい4色で保存された投稿があると、画面や Java を前の版に戻したときに、その色を知らずに画像化に失敗する。前の版に戻す前に、新しい4色を使った版が無いことを確かめる（または色の対応だけを残す）。DB の V11 は戻さない（追加だけなので、前の画面・Java からも読み書きできる）。

## 10. 決定事項（ADR）

- 新しい ADR は作らない。判断はすべて既存の ADR の範囲（ADR-0005: 二重実装は fixtures で揃える／ADR-0008・0009: 画像生成と候補／ADR-0010: テンプレートは変えない）。
- 背景写真の保存先は `backgrounds/` のまま（管理者だけが書ける保存先に、API関数が service role で複製する）。メンバーが書ける `posts/` は使わない。
- 業務の判断として梶原さんに確認する余地を残す点（要件の範囲外・未決）: AI が作った背景だけで30枚を埋めないための上限（30枚のうち N 枚まで）を設けるか。いまは共通の30枚だけで、管理者が「使わない」で整理する。
