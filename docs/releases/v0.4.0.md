# v0.4.0（2026-11-03）

## 業務上の変更（ドメインの言葉で）
- REQ-007: 最後のスライドの画像を設定画面でアップロードする（REQ-002 BR-002-15・AC-002-15 を置き換え）
  - 最後のスライドの真ん中に並べる画像を、管理者が投稿の型の設定（S-15）で2枚までアップロードできる。選び直す・外す（後ろの画像が前に詰まる）ができ、保存すると投稿の型の設定の新しい版になる
  - アップロードした画像は、画面で縦横比 4:5 の中央を切り抜き、800×1000px の JPEG にして保存する。切り抜くと 400×500px に満たない画像と、PNG・JPEG 以外のファイルは受け付けない
  - 最後のスライドは、1枚目を左・2枚目を右に並べる（1枚なら真ん中に1枚、0枚なら画像の欄を出さない）。テンプレートは `niijima@1` のままで、見た目（枠 400×500px・間隔 40px）は変えていない
  - 承認のときに「公開済みの投稿のうち新しい2件の表紙」を自動で選ぶのはやめた。載せる画像は、その投稿の版が使った投稿の型の設定の版（下書きを保存した時点の最新の版）で決まる。承認を依頼した後・承認した後に設定の画像を変えても、その投稿は変わらない
  - 編集の画面のプレビュー・投稿の表示・承認の画面にも最後のスライドの画像が出る（これまでは承認するまで空だった）
  - この版より前に承認した投稿は、承認したときに記録した過去の投稿の表紙のまま画像化する（記録が0件なら画像の欄なし）
  - 最後のスライドの画像が見つからずに画像化に失敗したときは、「最後のスライドの画像が見つかりません。管理者が画像を設定し直したあと、下書きに戻して保存し直してください」だけを表示する（再実行では直らないため「今すぐ再実行でやり直せます」は付けない）
- 不具合の修正: 画像化の失敗のとき、投稿の表示とカレンダーで対処方法の案内が2回出ていたのを1回にした
- 写真の投稿（REQ-001・REQ-005）と、表紙・中のスライド（REQ-002・REQ-006）の描画・公開は変えていない

## API 変更
- RPC `save_post_style_settings`: 末尾に `p_closing_images text[] default '{}'` を追加。古い署名の関数は削除した（PostgREST の呼び分けの曖昧さを避けるため）。古い画面が名前付きで呼んでも失敗はしないが、最後のスライドの画像0枚の版として保存される（画像が黙って外れる。デプロイ後は開いている画面を再読み込みする）。新しいエラー: 42501（保存先の形が自分の団体の `style/{名前}.jpg` でない）、22023（null・null の要素・3枚以上・同じ保存先が2つ）
- RPC `approve_post`: 引数・戻り値は変えていない。過去の投稿を選んで記録する処理を外した
- 削除: 内部関数 `app.past_post_cover`（`approve_post` だけが使っていた）
- Web API（API関数）の変更なし

## データベース
- マイグレーション: `V12__closing_images.sql`（追記型）
  - 新しい表 `post_style_closing_images`（設定の版ごとの最後のスライドの画像。追記のみ・RLS は自団体のメンバーが読むだけ・書くのは RPC だけ）
  - 既存データの変換なし。既存の設定の版には画像を足さない（改修前の承認が画像なしで描かれる前提のため）。`approval_past_posts` の行は残し、読むだけにする
  - Storage のポリシーは変えていない（`style/*.jpg` は既存のポリシーで管理者が書ける）
- 適用の手順（設計書 REQ-007 7章。この順を守る）
  1. tick を止めた状態にする（いまは Meta の準備待ちで tick・daily とも disabled のまま）。リリースノート・Excel をコミットしてブランチを push し、**V12 をこれ以上変えない状態にしてから** migrate を起動する（適用後に V12 を変えると checksum が合わず、次の migrate の validate が通らない）
  2. このリリースのブランチを ref に指定して migrate を起動し、v12 の適用を確かめる。確かめること: `flyway_schema_history` の version 12 が success、`save_post_style_settings` が1つだけで引数が8個（`pg_proc`）。RPC が 404 になるときは `notify pgrst, 'reload schema'`
  3. main に push（CI）→ Pages にデプロイ（画面を V12 より先に出すと、投稿の型の設定とプレビューが動かない）。デプロイ後、S-15 や編集の画面を開いている人は**再読み込みしてから**操作する（古い画面で設定を保存すると、画像0枚の版ができる）
  4. 管理者が S-15 で最後のスライドの画像を設定する
  5. 改修前に保存したテンプレートの投稿を保存し直す（画像の無い設定の版を使っているため、保存し直すまで画像は0枚。本番はまだ公開済みの投稿が無いので、改修前の承認の過去の投稿の記録もすべて0件＝画像の欄なしで描かれる）
     - 下書き: 開いて保存し直す
     - 承認待ち: 修正指示で下書きに戻して保存し直し、承認を依頼し直す
     - 予約中: 予約を取り消して（下書きに戻る）保存し直し、承認し直す
     - 失敗: 下書きに戻して保存し直し、承認し直す（「今すぐ再実行」では古い設定の版のまま描かれる）
     - 対象があるかは、カレンダー（S-01）でテンプレートの投稿を状態ごとに見て確かめる
  6. tick を有効にするのは、これまでどおり Meta の準備のあと（5 が済んでから）
- ロールバック手順: Java・画面だけを戻さない（V12 の後の承認は過去の投稿を記録しないので、旧 Java は最後のスライドを画像0枚で描き、作り直されない）。戻すときは、前に進める形の V13（新しい8引数の `save_post_style_settings` を先に drop してから旧署名を作り直す・旧 `approve_post`・`app.past_post_cover` を作り直す）と一緒に戻す。V12 のファイルは消さない（適用済みのマイグレーションが手元に無いと validate が失敗する）。新しい表は残してよい

## 既知の問題・次回対応
- 改修前に承認して失敗し、そのあと破棄した投稿は、投稿の表示では記録した設定の版（画像なし）で描く（公開されないので画像化とのずれは実害なし）
- 最後のスライドの画像のテンプレートへの差し込みの名前は `pastPosts` のまま（niijima@1 の契約）。`niijima@2` を作るときに名前を直す
- 画像の画素数（400×500px 以上・800×1000px 以下）はサーバーでは確かめない（画面で確かめる。Storage に書けるのは自団体の管理者だけ）
- 変換中に保存ボタンを押せなくしたことの E2E は無い（タイミングの再現が難しいため）
